> 状态：**执行中**
> 日期：2026-09-19

## 1. 模型说明

本文件是 [docs/shell-parallel-exec-plan.md](./shell-parallel-exec-plan.md)（下称"总案"）的**当前执行视图**：

- 编排模型按 2026-09-19 用户指令定为：**主 agent（当前会话模型）任总指挥兼执行者 + 至多 2 个 coding-agent（CA）并行槽**；若两个 CA 无法并行（限流/异常），按 §7 探针规则回归"主 agent 单执行者串行"。
- 总案 **§3 全局单点锁清单（L1~L9）与 §4.3 执行 agent 通用纪律继续有效**，本文件不重述原文，仅在具体卡上标注锁持有关系。
- 总案 §2 的 6 并发执行池模型与 §4.2 波次表由本文件 §3 取代（6 并发模型留作备查，恢复时可直接沿用）。
- 本文件同时是**执行台账**（§10）：每卡完成后由主 agent 回填，与各流方案文档的 §执行记录 同步。

## 2. 角色与纪律

### 2.1 主 agent（MAIN）

总指挥 + 执行者 + **唯一 git 写入者**。职责：派卡与补位调度；亲自执行所有 MAIN 卡；持有 L1~L9 全部锁；验收 CA 产出并代为提交；执行三次 install（§5）；执行各流收口与根 `pnpm verify`（L8）；回填执行记录（§6）。

### 2.2 coding-agent（CA，至多 2 槽）

纪律照总案 §4.3，结合本模型明确为：

1. 禁止 `git add/commit`；
2. 禁止 `pnpm install`（本模型下三次 install 全部由 MAIN 执行，CA **永不** install）；
3. 只写任务卡文件所有权清单内的文件；
4. 门禁只跑**应用级命令**（`cd apps/server && go build/vet/test` 或 `pnpm --filter <包名> test/typecheck`），禁止根 `pnpm verify`、禁止根 `pnpm test:e2e`；
5. 完工报告：改动文件清单 / 验收命令输出摘要 / 偏差说明；
6. 遇瞬时失败（限流、并发干扰）原位重试一次再上报。

补充：MAIN 验收 CA 产出时可追加更大范围门禁（如 site e2e project、构建产物断言），该追加门禁的执行者是 MAIN，不占 CA 槽。

### 2.3 执行者标注规则

| 标注   | 适用卡                                                                                                                                                                                                                 |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CA`   | 目标明确、文件所有权自包含、验收命令简单、新写代码为主（h5 H1.B/H2.x、miniapp N2.x/N4b、site P3/P4.1、mobile M2.x、desktop D1/D2 等新模块卡）                                                                          |
| `MAIN` | 触碰单点/横切文件（go.mod L7、main.go、根 AGENTS.md L2、根 playwright.config.ts L3、scripts/verify.sh L4、ci.yml L5、turbo.json L6）；精细重构（server S2/S3/S4/S5）；涉及架构判断或跨卡协调的卡；**所有收口卡与提交** |

## 3. 全局序列与波次

### 3.1 排序原则

1. 尊重各流流内 DAG（见总案 §4.1）；
2. 进行中的流优先收尾：server S1.2 与 h5 H1.B 是链头，进第一波；
3. 流间先后**对总案默认建议（server→h5→site→miniapp→mobile→desktop 严格流串行）做如下调整**：MAIN 槽保 server 关键链一贯到底，CA 双槽跨流滚动消化各流新模块卡。理由：① 3 槽模型下严格流串行会让 2 个 CA 槽在 server 阶段空转（server 12 卡中仅 S6.1~~6.3 三张可外发）；② 六流文件所有权按 app 目录天然隔离，共享单点已全部被 L1~~L9 覆盖，跨流并行零冲突；③ 收口顺序由锁依赖自然形成（h5 H3.1 → desktop D4 → miniapp N7.1 三次 install 有序，site P8.1 因 L5 等待 D4 的 ci.yml 而自然成为总收口）。

### 3.3 滚动补位规则（W5 起，不穷举后续波次）

1. **槽空即补**：任一侧槽完工验收后立刻补位，不等整波结束；补位只从"依赖已满足"的就绪队列取卡。
2. **同飞互斥校验**：新卡与全部在飞卡的文件所有权必须互不相交；任一 app 的 `package.json` 为流内单点，同一时刻仅一张在飞卡持有（miniapp 持有序：N4a → N5a → N5b；h5：H2.A；desktop：D2）。
3. **MAIN 槽队列**（server 关键链优先，之后按锁依赖序）：
   `S3.1 → S4.1 → S5.1 → S5.2 → H3.1(L1#1+L8) → S6.9(L8) → M1.1 → M1.2 → M1.3 → M3.1 → M3.2 → M3.3 → H4.1(L3) → H5.1(L2) → M4.A(L4) → D4(L1#2+L3+L4+L5+L8) → N6.1(L2) → N7.1(L1#3+L4+L6+L8) → N7.2 → P6.2 → P8.1(L5+L8，总收口)`
4. **CA 槽就绪队列**（按序扫描，依赖未满足则跳过，每轮重扫）：
   `H2.A → H2.B → H2.C → P4.1 → P4.2 → N3 → N4a → N4b → P5.1 → P5.2 → N5a → N5b → N6.2 → D3 → P6.1 → P7.1 → P7.2 → S6.1 → S6.2 → S6.3 → M2.A → M2.B → M2.C → M4.B`
   （M2.A/B/C 待 M1.3 接口冻结后解锁；S6.1~6.3 待 S4.1+S5.2 完成后解锁；N3/N4x 待 N2.x 全部完成后解锁；D3 待 D1+D2 后解锁；M4.B 待 M3.3 后解锁。）
5. **L8 冻结窗口**：跑根 `pnpm verify` 前暂停派发新 CA 卡，等在飞 CA 卡完工验收后执行；verify 期间仅允许 MAIN 修复性写入。流内中间阶段不跑根 verify（以应用级门禁代替），统一在各流收口卡执行——此条覆盖 server 方案阶段 2/3/4"各跑一次 verify"的原要求，理由是 L8 全局串行与 CA 并行写入存在竞争。
6. **收口卡隔离**：收口卡（S6.9 / H3.1 / P8.1 / D4 / N7.1）执行期间，CA 槽不得同时跑同 app 的任何卡。

## 6. 提交纪律与执行记录回填

1. **主 agent 是唯一 git 写入者**。每卡验收绿后：`git add <该卡文件所有权路径> && git commit --no-verify -m "<§4 建议提交信息>"`（Conventional Commits）。`--no-verify` 原因见总案 L9：lint-staged 的 stash/restore 周期会覆盖并行 agent 的未提交写入；prettier/风格由各卡验收门禁自行把关。
2. CA 产出由 MAIN 按 §2.2 验收（可追加更大范围门禁）后代为提交；CA 完工报告并入提交前的验收记录。
3. **执行记录回填两处**：每卡完成后回填 ① 该流方案文档的 §执行记录表；② 本文件 §10 执行台账。回填随该卡同一提交完成（该流收口卡统一回填亦可，但不得晚于收口提交）。
4. 生成物（`apps/*/src/api/generated/`、`controllers.gen.ts`、`apps/server/gen/`）禁止手改；本轮 57 卡均不涉及契约变更，若某卡发现必须改契约，立即停工上报总指挥另行立项。

## 7. CA 并行性探针与降级规则

1. W1 即**探针波**：2 张 CA 卡（h5 H1.B、site P3，跨流、零相交）+ MAIN 1 张（server S1.2）。
2. 若 2 张 CA 卡顺利并行完成 → 维持「MAIN 1 + CA 2」3 并发模型。
3. 若任一 CA 卡出现限流/取消类失败，**原位重试一次**；重试仍失败 → 该卡退回 MAIN 串行队列（按依赖序插入 MAIN 队列），§10 台账备注「回归串行」，同时 CA 调度降为 1 槽观察一波。
4. 若降槽后该 CA 槽仍失败 → 全面回归「主 agent 单执行者串行」，MAIN 队列按 §3.3 的 MAIN 序与 CA 就绪队列合并（依赖优先、关键链优先），台账逐卡备注。
5. 探针结论与每次降级都必须在 §10 台账备注列留痕。
